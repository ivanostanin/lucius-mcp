## Intent

**Problem:** The hierarchy E2E tests need to verify test-case assignment and deletion without directly calling the client or a service-only test adapter. Existing full-tree listing is the wrong verification primitive for a single suite in a shared, parallel-test environment.

**Approach:** Keep the targeted suite-content service capability, expose it as a genuine thin MCP tool, and make hierarchy E2Es use only registered tools. Assignment uses the targeted tool; deletion polls the real hierarchy-list tool for exact created IDs because nested suite names are not indexed reliably. Each test uses run-unique resources, explicit project context, bounded polling, and the existing cleanup tracker.

## Boundaries & Constraints

**Always:** Preserve Thin Tool/Fat Service separation; expose structured suite metadata plus directly assigned test-case IDs; keep the existing bounded full-tree listing implementation; add unit, integration, registry/schema, and live E2E coverage; make every E2E assertion invoke a registered tool rather than a client or service method directly.

**Ask First:** Adding non-hierarchy capabilities, changing TestOps client defaults, or changing cleanup behavior outside this test module.

**Never:** Call `AllureClient`, `_client`, private service methods, or generated/raw API methods from hierarchy E2Es; add a test-only read path; share fixed names or mutable state between E2E cases; suppress persistent lookup errors as absence.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|----------------------------|----------------|
| Targeted contents lookup | Existing suite ID and optional tree ID | Tool returns suite ID and direct test-case IDs | Typed not-found error when node is absent or does not match ID |
| Assignment E2E | Run-unique suite and case were assigned through the assignment tool | Targeted contents tool reports that case ID | Fail if the ID is missing; cleanup tracks both resources |
| Cascaded deletion E2E | Parent and child have run-unique IDs | Hierarchy-list tool eventually omits both IDs | Fail after bounded deadline; the list service handles transient snapshot reads |
| Concurrent E2E workers | Same TestOps project, independent generated IDs/names | No test reads or deletes another test's resource | Pass explicit project/tree context where available and track every created resource |

## Design Notes

The targeted read is a legitimate user capability: an agent assigning test cases needs a cheap way to inspect a suite without rendering the entire project tree. The service owns the API call and normalization; the tool only dispatches and renders it. E2E code consumes the same tool contract that an agent receives, so it no longer creates a test-only abstraction boundary.

The targeted tool returns its resolved tree ID so callers can pin subsequent operations. Its optional expected-name guard avoids a missing-node contents read when the index has a reliable entry. Nested suite names are not reliably indexed in the live TestOps environment, so deletion E2Es instead poll the public list tool for the UUID-derived suite IDs; this directly exercises the bounded shared-hierarchy traversal.
